    Running operations from the command line¶

    SpecCommand serves every spec in a registry as one management command, with one subcommand per spec. An operator runs an operation as a named user, with arguments as options, and gets its presented result as a table or as JSON Lines:

    $ python manage.py notes rename-note --as-user 1 --pk 1 --title Final --json
{"id":1,"title":"Final"}

    The run goes through dispatch as every other transport's does: the same shape check and Validator, the same permission checks, enforced, for the user --as-user names, the same presenter. It needs Django and nothing else.

    from django_spec_cli import ExitCode, SpecCommand, exit_code_for

    Installing¶

    pip install django-spec-cli

    It installs django-service-specs, the kernel whose specs it serves, from 0.10.0, on Python 3.10 and Django 4.2 or later. The command line was the kernel's commands/ subpackage, and moved here so the kernel carries no transport.

    What it is not¶

    The command is not an authorization boundary. Whoever can run manage.py can already run any code the project can, open manage.py shell, and name any user they like with --as-user. What the command offers is mistake prevention and attribution: every run is made as a named user, is checked against the permissions that user holds, and records that user wherever the operation records who acted. Refusing to run an open spec would stop nobody, so the command reports open specs instead.

    Declaring a command¶

    A project declares the command by subclassing, in one of its own apps' management/commands/ modules, and names the registry. The module's name is the command's:

    def whoami(*, user: Any) -> str:
    """The username of the user the command runs as."""
    return user.get_username()


notes = SpecRegistry()
notes.register("rename_note", rename_note_spec)
notes.register("list_notes", list_notes_spec)
notes.register("whoami", ServiceSpec(service=whoami, permissions=[Unrestricted()]))


# yourapp/management/commands/notes.py
class Command(SpecCommand):
    registry = notes

    One project can serve two registries as two commands, each with its own name. The registry is read when the command's parser is built, on every run; a command naming none is refused then with ImproperlyConfigured, as is a registry where two names would be one subcommand (a_b and a-b).

    A registry whose callables read a seed of their own - an affordance's when, a selector - names the seeds on the class, as SpecView does: pool_seeds = DEFAULT_POOL_SEEDS.extend(tenant=current_tenant). Without it a callable asking for a seed nobody registered fails as it would in dispatch.

    The command does not need django_spec_cli or django_service_specs in INSTALLED_APPS. Listing django_spec_cli adds the system check.

    Subcommands and their options¶

    Each registry entry is a subcommand named after it, with each _ shown as -: rename_note is rename-note. Its options are the spec's parameters, spelled by add_spec_arguments: --due-at for due_at, a --flag/--no-flag pair for a boolean, and an array as a repeated option, --tag a --tag b. Every value reaches coerce_flat as the string typed, and is refused as a query string's would be. A value that starts with - is read by argparse as an option, so it is attached with an equals sign: --tag=-x.

    manage.py notes --help lists the subcommands, each with the first paragraph of its service's or selector's docstring and whether it reads or writes, or its registered name when the function says nothing. manage.py notes rename-note --help lists its options, with (required) where leaving one out is refused. On a partial spec, that is only what names the row: the Validator's fields may be left out, as dispatch allows.

    Some parameters have no option:

    • A key the server fills, one a kwargs provider is annotated to answer (server_owned_keys), since a value sent for it would be dropped.
    • A parameter with no flat spelling: an object, an array of objects or of arrays, and a file. The subcommand's help names them. A spec that requires one, such as any many spec, cannot be run from the command line.

    No option is matched by a prefix. Argparse reads --titl as --title by default, and beside a parameter as_user_id a mistyped --as-user-i 7 would have been read as that parameter rather than refused. Here every prefix is refused, Django's own options' included.

    A spec parameter may not map to an option the command owns: --as-user, --json, --table, or one of Django's, such as --verbosity or --settings. manage.py reads --settings from anywhere on the line, so a spec option of that name would configure Django instead. Such a parameter is refused with ImproperlyConfigured when the parser is built.

    The user a run is made as¶

    --as-user is required. There is no default user, no system user of the command's own, and no fallback to an anonymous user. Its value goes through the command's resolve_as_user method, which by default looks a user up by primary key with resolve_principal. A project whose runbooks name people by username overrides the method:

    class ByUsername(SpecCommand):
    registry = notes

    def resolve_as_user(self, value: str) -> Any:
        users = get_user_model()
        try:
            return users.objects.get(username=value)
        except users.DoesNotExist:
            raise PrincipalUnavailable(f"No user named {value!r}.") from None

    The contract is: return a user, or raise PrincipalUnavailable, which ends the run with exit status 5. Anything else the method raises is a bug in it, and propagates with its traceback. An override need not refuse a deactivated user itself, since dispatch refuses one whatever the lookup returns.

    The command passes no Grant, so the spec's permission checks run for that user as they would for a request from them:

    $ python manage.py notes rename-note --as-user 2 --pk 1 --title Final
CommandError: Only the note's owner may rename it.
$ echo $?
4

    Output¶

    A run's result goes through the spec's presenter, then is written in one of two formats, decided in this order:

    1. --table or --json on the command line.
    2. The SPEC_CLI_OUTPUT setting: "table" or "json" pins one project-wide; "auto", the default, leaves it to the next step.
    3. A table when stdout is a terminal, JSON Lines when it is a pipe or a file.

    That last step means an interactive run and CI print different things by default, which is what the flag and the setting are for:

    $ python manage.py notes list-notes --as-user 1 --json
{"id":1,"title":"Final"}
{"id":2,"title":"Shopping"}
$ python manage.py notes list-notes --as-user 1 --table
id  title
 1  Final
 2  Shopping

    The table's columns come from the spec's Output, never from the first row; see render_table for what a field's marking does to them. JSON Lines are written one row at a time, but present builds a list result whole before the first row is written, so a large read is held in memory once, as an HTTP response holds it. A service that returns nothing writes nothing.

    Exit codes¶

    A refusal ends the run with a CommandError whose message goes to stderr and whose ExitCode is the process's exit status. The codes are a public contract, for a script to branch on:

    Code ExitCode The run
    0 SUCCESS ran, and its result was written
    1 ERROR failed in a way nobody declared: the traceback is printed
    2 USAGE never started: the command line was malformed
    3 INVALID_ARGUMENTS InvalidArguments, ServiceValidationError, any other DispatchError
    4 NOT_PERMITTED NotPermitted
    5 PRINCIPAL_UNAVAILABLE PrincipalUnavailable: no such user, or a deactivated one
    6 NOT_FOUND the row named does not exist, or the service raised ServiceNotFound
    7 CONFLICT ServiceConflict, and ActionUnavailable with its code in the message
    8 INPUT_REQUIRED AdditionalInputRequired
    9 REFUSED any other ServiceError

    exit_code_for is the mapping, for a project that runs specs from a command of its own.

    An invalid argument prints one line per refused field, after its path:

    $ python manage.py notes rename-note --as-user 1 --pk 1
CommandError: Invalid arguments.
title: This field is required.
$ echo $?
3
$ python manage.py notes rename-note --as-user 1 --pk one --title Final
CommandError: Invalid arguments.
pk: Enter a whole number.
$ echo $?
3
$ python manage.py notes rename-note --as-user 1 --pk 99 --title Final
CommandError: Not found.
$ echo $?
6

    A command line cannot ask a question, so AdditionalInputRequired ends the run with code 8 and names the options its schema asks for. The operator, or a script that knows the answer, runs the command again with them.

    Through call_command the CommandError is raised to the caller rather than printed, with the code as its returncode. A malformed command line is a CommandError there too, as Django makes every parser error, with returncode 1 rather than 2.

    Open specs: --explain and the system check¶

    whoami is open to every active user, which is what it is for:

    $ python manage.py notes whoami --as-user 2 --json
"grace"

    --explain runs no spec. It prints one line for each spec the command serves that authorizes nothing, every check it declares being Unrestricted:

    $ python manage.py notes --explain
'whoami' in manage.py notes authorizes nothing: every permission check it declares is Unrestricted, so any active user named by --as-user may run it.

    Listing "django_spec_cli" in INSTALLED_APPS reports the same sentence from manage.py check, as django_spec_cli.W001, once per open spec of every SpecCommand in the project, and a command that could not be loaded to be checked as django_spec_cli.W003. There is no W002: a spec with an empty permissions is refused when it is built, so none reaches a registry. Both are warnings, and SILENCED_SYSTEM_CHECKS silences one by id.

    Until the kernel removes its own copy of the command, kernel 0.10.x still registers django_service_specs.W001 and W003, over its own SpecCommand class rather than this package's. A project that lists both "django_service_specs" and "django_spec_cli" sees both ids, the kernel's for commands still subclassing its copy and this package's for commands subclassing django_spec_cli.SpecCommand, and a command that cannot be loaded gets a W003 from each. A project that moves its imports here and lists only "django_service_specs" gets no check for the moved commands at all, so list "django_spec_cli".

    A SpecCommand keeps Django's system checks on, so on the command line the report is printed to stderr before every run of every command. The runs on this page are shown without it; in a project listing the app, each would be preceded by the warning for whoami. call_command skips system checks for every command but check, so a command run through it does not print them.

    What it does not do¶

    • No payload file. Arguments are options; an object or a list of rows has none, and there is no --from-json.
    • No --dry-run. A run that resolves and validates without running the service is not offered.
    • Sync only. The command dispatches with dispatch, never adispatch, so an async def service is run as dispatch runs one.
    • No transaction of its own. A spec's atomic is dispatch's to honour.
    • No Typer. The command is argparse, as manage.py is, and needs nothing beyond Django.
